# Feature Specification: ダイブサイト（ポイント）マスタ

**Feature Branch**: `011-dive-sites-master`

**Created**: 2026-06-15

**Status**: Draft

**Input**: User description: "ダイブサイト（ポイント）マスタ — 今は location が自由入力なので「大瀬崎」「伊豆 / 大瀬崎」が別物になります。マスタ化すると「このポイントで何本・平均透明度・ベストシーズン」が出せて、ログの蓄積価値が大きく上がります。todo の管理画面のマスタ管理対象としても自然で、rules/sql.md の dive_sites 設計例とも一致します"

## Clarifications

### Session 2026-06-16

- Q: サイトを選択したログと自由入力ポイント名（`location`）の関係は？ → A: ログは `dive_site_id` を参照し、表示名は常にマスタから取得する。サイト選択時は `location` を保持しない。自由入力ログのみ `location` を使う（`dive_site_id` は null）
- Q: ダイブサイトの同一性（重複防止）の判定キーは？ → A: 名称のみで一意（同名サイトは登録不可。区別が必要な場合は名称自体で区別する）
- Q: サイト別実績（本数・平均透明度・ベストシーズン）の表示場所は？ → A: ダイブサイト詳細ページを新設してそこに表示し、ログ詳細のサイト名からリンクで遷移する
- Q: 「ベストシーズン」の算出・提示方法は？ → A: 月別の潜水本数の分布を集計し、本数が多い月（上位）を「よく潜る時期」として提示する（コンディション評価は将来拡張）
- Q: ベストシーズンの上位件数とデータ不足の閾値は？ → A: 本数が多い月の上位 3 ヶ月（同数は月昇順）を提示。対象ログが 3 本未満のときは傾向を出さず「傾向を出すにはログが不足」と表示する
- Q: ポイント名検索はサイト参照ログにも効くか？ → A: 効く。ポイント名検索はサイト名・自由入力名の双方に一致する（サイト参照ログは `location` が null でも、サイト名で見つかる）
- Q: FR-007/008（運用者の追加・編集・統合）と SC-004 の扱いは？ → A: 本機能ではスコープ外。別機能「管理画面」＋管理者ロールで実装し、本機能ではマスタ初期データを seed で投入する（FR-009 の削除制限は DB の `on delete restrict` で安全網のみ先行確保）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - ログ記録時にダイブサイトを一貫した名前で選ぶ (Priority: P1)

ダイバーであるユーザーは、ダイブログを記録・編集するとき、**ポイント名やエリアで検索して登録済みのダイブサイトを選ぶ** か、マスタに無いポイントは **従来どおりポイント名を自由入力する** か、どちらでも記録できる。マスタから選んだログ同士は「大瀬崎」「伊豆 / 大瀬崎」「おおせざき」のような表記ゆれがなくなり、同じサイトとして確実に集計される。マスタ参照と自由入力は同居する。

**Why this priority**: 表記の一貫性は、本機能が生むすべての価値（サイト別集計・蓄積価値）の前提。これ単体でも「ログのポイント名が揃う」という価値が成立し、以降のストーリーの土台になる。検索選択と自由入力の同居により、既存ユーザーの記録体験を妨げずに導入できる。

**Independent Test**: ダイブサイトが数件登録された状態で新規ログ作成画面を開き、検索してサイトを選択して保存 → ログ詳細・一覧に選んだサイト名が表示される。別途、サイトを選ばず自由入力でも保存できることで単独テスト可能。

**Acceptance Scenarios**:

1. **Given** ダイブサイトが登録済み, **When** ダイブログの新規作成でサイトを選択して保存, **Then** そのログは選択したサイトに紐づき、一覧・詳細に統一されたサイト名で表示される
2. **Given** あるサイトに紐づいた既存ログ, **When** 編集画面を開く, **Then** 現在のサイトが選択済みの状態で表示され、別のサイトに変更して保存できる
3. **Given** 同じサイトを選んだ複数のログ, **When** そのサイトで集計する, **Then** 表記ゆれなく同一サイトの実績としてまとめられる
4. **Given** ログ作成画面のサイト選択欄, **When** ポイント名やエリアのキーワードを入力, **Then** 一致するダイブサイト候補が絞り込まれて表示され、その中から選べる
5. **Given** 潜ったポイントがマスタに無い, **When** サイトを選ばずにポイント名を自由入力して保存, **Then** 自由入力のポイント名でログが記録される（マスタ参照なしでも記録できる）

---

### User Story 2 - ダイブサイトごとの実績を確認する (Priority: P2)

ユーザーは、ダイブサイトについて「自分がこのポイントで何本潜ったか」「平均透明度」「ベストシーズン（よく潜られている時期 / コンディションの良い時期）」を確認でき、ログを貯めるほど各ポイントの傾向が見えるようになる。

**Why this priority**: マスタ化の主目的である「蓄積価値の向上」を体現するストーリー。US1（一貫した紐付け）が前提で、ログが貯まるほど価値が増す。

**Independent Test**: 同一サイトに複数のログ（異なる日付・透明度）が紐づいた状態で、ダイブサイト詳細ページを開き、本数・平均透明度・季節傾向が正しく集計されることで単独テスト可能。

**Acceptance Scenarios**:

1. **Given** あるサイトに自分のログが複数件紐づいている, **When** ダイブサイト詳細ページを開く, **Then** 潜水本数・平均透明度・潜水時期の傾向（ベストシーズン）が表示される
2. **Given** 透明度が未記録のログが混在する, **When** 平均透明度を集計する, **Then** 値のあるログのみで平均が計算され、未記録分は除外される
3. **Given** 自分のログが 0 件のサイト, **When** ダイブサイト詳細ページを開く, **Then** 実績がない旨が表示され、本数 0 として破綻なく表示される
4. **Given** サイトに紐づくダイブログの詳細, **When** ログ詳細に表示されたサイト名を選ぶ, **Then** そのダイブサイト詳細ページへ遷移する

---

### User Story 3 - 管理画面でダイブサイトマスタを管理する (Priority: P3)

マスタを管理する権限を持つ運用者は、管理画面からダイブサイトの追加・編集・統合（重複した表記ゆれサイトを 1 つにまとめる）を行い、マスタの品質を保てる。

**Why this priority**: マスタの増加・重複は運用で必ず発生するため、長期の品質維持に必要。ただし US1/US2 が動けば当面はシード済みデータで価値が出せるため P3。

**Independent Test**: 管理画面でサイトを新規追加 → ログ作成画面の選択肢に現れること、2 つの重複サイトを統合 → 両方に紐づいていたログが 1 つのサイトに集約されることで単独テスト可能。

**Acceptance Scenarios**:

1. **Given** 管理権限を持つ運用者, **When** 新しいダイブサイトを登録, **Then** ユーザーのログ作成・編集画面の選択肢にそのサイトが現れる
2. **Given** 表記ゆれで重複した 2 つのサイト, **When** 一方へ統合, **Then** 統合元に紐づいていたログがすべて統合先に付け替わり、統合元は一覧から消える
3. **Given** 既存ログから参照されているサイト, **When** そのサイトを削除しようとする, **Then** 参照中である旨が示され、誤って実績が失われない（統合または参照解消を促す）

---

### Edge Cases

- 潜ったポイントがマスタに存在しない場合 → 従来どおりポイント名を自由入力して記録できる（マスタ参照と自由入力は同居する）。表記ゆれは将来マスタへ統合できる
- 既存の自由入力 `location`（過去ログ）→ そのまま自由入力として保持し、新規記録からマスタ参照を任意で選べる段階移行とする（過去ログの強制変換はしない）
- 検索キーワードに一致するサイトが無い場合 → 候補が空であることを示し、自由入力で記録する導線を妨げない
- 同名・ほぼ同名のサイトが重複登録された場合 → 統合（US3）で解消する
- 同じポイントでも地域表記の粒度が違う（「大瀬崎」と「伊豆 / 大瀬崎」）→ 地域（エリア）と名称を分けて持ち、表示は組み合わせる
- ベストシーズンを判定できるだけのログがまだ少ない場合（対象ログが 3 本未満）→ 傾向を出さず「傾向を出すにはログが不足」と表示し、誤った季節を断定しない

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは「ダイブサイト」を、ポイント名・エリア（地域）・国を持つ参照用マスタとして管理できなければならない
- **FR-001a**: ダイブサイトの名称は一意でなければならない（同名サイトの重複登録を許可しない。区別が必要な場合は名称自体で区別する）
- **FR-002**: ユーザーはダイブログの作成・編集時に、登録済みダイブサイトから 1 つを選択してログに紐づけられなければならない
- **FR-002a**: ユーザーはサイト選択時に、ポイント名・エリア（地域）をキーワードで検索して候補を絞り込めなければならない
- **FR-002b**: ダイブサイトの選択候補・表示は、名称とエリアを組み合わせて識別できる形（例: 「伊豆 / 大瀬崎」）で示されなければならない
- **FR-003**: ダイブログ一覧・詳細では、紐づくダイブサイトの名称が統一された表記で表示されなければならない
- **FR-004**: システムは、あるダイブサイトに対する利用者本人の潜水本数を集計して表示できなければならない
- **FR-005**: システムは、あるダイブサイトに紐づく利用者本人のログから平均透明度を算出して表示できなければならない（透明度未記録のログは平均計算から除外する）
- **FR-006**: システムは、あるダイブサイトに紐づくログの月別潜水本数の分布を集計し、本数が多い月の上位 3 ヶ月（同数は月昇順）を「よく潜る時期（ベストシーズン）」として提示できなければならない。対象ログが 3 本未満のときは傾向を出さず、その旨を表示する
- **FR-006a**: システムはダイブサイト詳細ページを提供し、サイト別実績（本数・平均透明度・ベストシーズン）を表示しなければならない。ダイブログ詳細のサイト名からこのページへ遷移できなければならない
- **FR-007**: マスタ管理権限を持つ運用者は、ダイブサイトの新規追加・編集ができなければならない（**本機能ではスコープ外** — 別機能「管理画面」+ 管理者ロールで実装。本機能ではマスタ初期データを seed で投入する）
- **FR-008**: マスタ管理権限を持つ運用者は、重複した 2 つのダイブサイトを統合でき、統合元に紐づいていたログはすべて統合先に付け替わらなければならない（**本機能ではスコープ外** — 別機能「管理画面」で実装）
- **FR-009**: 既存ログから参照されているダイブサイトは、参照を解消・統合しない限り誤って削除されてはならない（本機能では DB の `on delete restrict` による安全網のみ。削除 UI・統合導線は別機能「管理画面」で実装）
- **FR-010**: ユーザーはサイトを選択せず、ポイント名を自由入力してログを記録することもできなければならない（マスタ参照と自由入力は同居する）
- **FR-011**: 既存の自由入力ポイント名（過去ログ）は変換されずそのまま保持され、本機能導入後も破綻なく表示され続けなければならない（マスタ参照は新規記録から任意で選べる段階移行）
- **FR-012**: ダイブサイトの実績（本数・平均透明度・ベストシーズン）は導出値として算出し、冗長には保存しない
- **FR-013**: マスタ参照と自由入力のどちらで記録されたログも、一覧・詳細・ポイント名検索で破綻なく扱えなければならない。ポイント名検索はサイト名・自由入力名の双方に一致する（サイト参照ログは `location` が null でもサイト名で見つかる）

### Key Entities *(include if feature involves data)*

- **ダイブサイト（マスタ）**: ダイビングのポイントを表す参照データ。属性は名称（必須）、エリア / 地域（例: 伊豆）、国（既定は日本）、任意の説明。**名称は一意**（同名サイトは登録不可）。全ユーザーで共有されるマスタ（同じポイントは全員にとって同一実体）。追加・編集・統合は運用者が行う（アプリ内のマスタ管理画面は別途「管理画面」機能で提供し、管理者の認可方式はその前提）。不変・低頻度更新のマスタ系で、ログから参照される側
- **ダイブログ（既存）**: 1 本のダイビング記録。ダイブサイトを **任意で** 参照する（`dive_site_id`、null 可）。サイト参照時は表示名を常にマスタから取得し、自由入力のポイント名は保持しない。サイト未参照時のみ自由入力のポイント名を使う（＝サイト参照と自由入力は排他で、ログ単位ではどちらか一方）。透明度・水温・潜水日など既存属性は変更しない（サイト参照の追加のみ）
- **サイト実績（導出値）**: あるダイブサイト × 利用者で算出する集計。潜水本数・平均透明度・潜水時期の傾向。保存せず、ログから都度算出する

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 同一ポイントに対するログのポイント名表記ゆれが 0 件になる（同じサイトを選んだログは 100% 同一名称で表示される）
- **SC-002**: ユーザーはログ作成時、サイト選択を含めても従来と同等かそれ以内の操作で（入力ステップを増やさずに）ポイントを指定できる
- **SC-003**: あるサイトに紐づくログの「本数・平均透明度・季節傾向」が、手計算と一致する（不一致 0 件）
- **SC-004**: 運用者は管理画面でサイトの追加・統合を、外部資料を見ずに完了でき、重複サイトの統合後の実績取りこぼしが 0 件（**本指標は別機能「管理画面」で達成。本機能スコープ外**）
- **SC-005**: マスタ導入後も、過去ログのポイント名が失われず表示・集計され続ける（表示破綻 0 件）

## Assumptions

- 本アプリは既存の認証機能（001-auth）とダイブログ機能（002-dive-log-crud）が利用できることを前提とする
- ダイブサイトは **全ユーザー共有のマスタ**（同じポイントは全員にとって同じ実体）とする。各ユーザーの実績集計は本人のログのみを対象とする（他人のログは集計しない）
- **マスタ参照と自由入力は同居する**。ユーザーはサイトを検索して選んでも、選ばずにポイント名を自由入力しても、ログを記録できる
- 既存の過去ログは自由入力のまま保持し、**新規記録からマスタ参照を任意で選べる段階移行**とする（過去ログの一括変換は本機能のスコープ外）
- サイト選択 UI はキーワードによるインクリメンタル検索で候補を絞り込む方式とする
- 「平均透明度」は既存ログの透明度（`visibility_m` 相当）を集計する。透明度の新規入力項目追加はスコープ外
- 「ベストシーズン」は月別潜水本数の分布から本数の多い月を示すものとし、コンディション（透明度等）評価や外部の海況データ取得はスコープ外（将来拡張）
- マスタの追加・編集・統合は **運用者（管理者）** が行う。アプリ内のマスタ管理画面は別機能「管理画面」（todo 起票済み）で提供する想定で、管理者ロール / 認可方式の新設はその前提作業。本機能の中心は「マスタを検索・選択してログに紐づける」「サイト別実績を見せる」ことで、US3 の管理 UI はその管理画面機能と連携する
- ポイント名・エリアは日本国内のダイビングポイントを主対象とする（海外サイトも登録可能だが初期シードは国内中心）
- `country`（国）はマスタ内部の属性（seed 投入）であり、選択 UI には表示しない（詳細ページでの表示は任意）。国コード値で保持する（既定は日本＝`JP`）
- 「ポイント」「ダイブサイト」「サイト」は本仕様内で同義（マスタ上のダイビングポイントを指す）
- 1 ログは最大 1 ダイブサイトに紐づく（1 本のダイビングは 1 ポイント。サイト未選択＝自由入力のみ、も許容）

## Dependencies

- 既存テーブル `dives` のポイント情報（現在は自由入力の `location`）と、本機能で導入するダイブサイトの関係を定義する必要がある
- マスタ管理 UI は「管理画面」機能（todo 起票済み）の一部として提供される想定。管理者の認可方式が前提条件になる
