# Feature Specification: プロフィール URL のニックネーム化

**Feature Branch**: `034-nickname-profile-url`

**Created**: 2026-07-12

**Status**: Draft

**Input**: User description: "マイプロフィールのidをニックネームにしたい　これって一意になっていて問題ないのであれば進めたい"

## 前提の確認（ユーザーの質問への回答）

**ニックネームは一意になっている**。ニックネームには正規化キー（小文字化 + 前後空白除去）による一意制約が既に存在し（021 で導入）、登録・変更時にも重複チェックが行われるため、URL の識別子として衝突しない。ただし次の 2 点は一意性とは別の論点として本仕様で扱う: (1) ニックネームは記号・スペースを含む自由な文字列のため URL に不向きな値が存在しうる、(2) ニックネームは設定から変更できるため URL が変わりうる。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - プロフィール URL がニックネームになる (Priority: P1)

ユーザーのプロフィールページ（自分・他人とも）の URL が、これまでの内部 ID（ランダムな英数字列）ではなくニックネームで表される。「◯◯さんのプロフィールを見て」と URL を共有したとき、誰のページか URL だけで分かる。アプリ内のプロフィールへの導線（ヘッダーのマイプロフィール・タイムラインの投稿者名・フォロー/フォロワー一覧・バディ表示・通知など）もすべてニックネーム URL に切り替わる。

**Why this priority**: この機能の主目的。URL の可読性・共有しやすさが直接の価値で、これ単体で完結する。

**Independent Test**: 任意のユーザーのプロフィールを開き、URL がニックネーム形式であること、アプリ内の各導線からニックネーム URL で遷移できることを確認すれば単体でテスト可能。

**Acceptance Scenarios**:

1. **Given** ログイン済みユーザー, **When** ヘッダーからマイプロフィールを開く, **Then** URL のユーザー識別部分が自分のニックネームになっている
2. **Given** タイムライン・フォロー一覧・ログのバディ表示など他ユーザーへの導線, **When** ユーザー名を選択する, **Then** ニックネーム URL のプロフィールページに遷移する
3. **Given** 日本語やスペースを含むニックネームのユーザー, **When** プロフィールを開く, **Then** URL 上は変換（エンコード）された形でも正しくそのユーザーのページが表示される
4. **Given** フォロワー・フォロー中の一覧ページ, **When** 開く, **Then** これらの URL もニックネーム基準になっている
5. **Given** 存在しないニックネームの URL, **When** アクセスする, **Then** 「ページが見つかりません」が表示される

---

### User Story 2 - 既存の ID 形式 URL の互換維持 (Priority: P2)

これまでに共有・ブックマークされた ID 形式のプロフィール URL にアクセスしても、リンク切れにならずそのユーザーのプロフィール（ニックネーム URL）へ転送される。

**Why this priority**: 既存リンクの破壊防止。US1 単体でも新規利用は成立するが、公開済みのリンクを壊さないために必要。

**Independent Test**: 既存の ID 形式 URL にアクセスし、ニックネーム URL へ転送されて同じプロフィールが表示されることを確認すれば単体でテスト可能。

**Acceptance Scenarios**:

1. **Given** ID 形式の既存プロフィール URL, **When** アクセスする, **Then** 同じユーザーのニックネーム URL へ転送され、プロフィールが表示される
2. **Given** ID 形式のフォロワー・フォロー中 URL, **When** アクセスする, **Then** 対応するニックネーム URL へ転送される
3. **Given** 存在しない ID 形式 URL, **When** アクセスする, **Then** 「ページが見つかりません」が表示される

---

### User Story 3 - ニックネーム変更と URL の関係 (Priority: P3)

ユーザーが設定でニックネームを変更すると、プロフィール URL も新しいニックネームに即時切り替わる。変更前のニックネーム URL は無効になる（そのニックネームは他のユーザーが取得でき、取得された場合はそのユーザーのページになる）。

**Why this priority**: ニックネームが変更可能である以上避けられない挙動の定義。US1/US2 の成立後に検証すればよい。

**Independent Test**: ニックネームを変更し、新 URL で表示できること・旧ニックネーム URL が無効（または別ユーザー）になることを確認すれば単体でテスト可能。

**Acceptance Scenarios**:

1. **Given** ニックネームを変更したユーザー, **When** マイプロフィールを開く, **Then** URL が新しいニックネームになっている
2. **Given** 変更前のニックネームの URL, **When** アクセスする, **Then** 「ページが見つかりません」が表示される（誰もそのニックネームを使っていない場合）
3. **Given** ID 形式の URL（変更前に共有されたもの）, **When** アクセスする, **Then** 変更後のニックネーム URL へ転送される（ID 経由のリンクは変更に影響されない）

---

### Edge Cases

- URL のパス区切りと衝突する文字（「/」等）を含むニックネーム → そのユーザーのプロフィールはニックネーム URL で表せないため、ID 形式 URL で引き続きアクセス可能とする（アプリ内導線も ID 形式にフォールバック）
- 予約されたパス名（ユーザー検索など、プロフィール以外の用途で使われるセグメント）と同名のニックネーム → 予約パスが優先され、該当ユーザーは ID 形式 URL にフォールバックする
- ID とニックネームの判別 → ID 形式（内部 ID のパターン）に一致する文字列は ID として解釈し、それ以外をニックネームとして解釈する。ID 形式と同じパターンのニックネームは新規・変更時に登録できないようにする
- 大文字小文字だけが異なる URL（例: /users/Taro と /users/taro）→ 一意制約と同じ正規化（小文字化）で同一ユーザーに解決する
- ニックネーム変更直後にアプリ内の古い導線（開きっぱなしの画面）から旧ニックネームへ遷移した場合 → 「ページが見つかりません」となる（ID 形式導線は影響なし）

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムはプロフィールページ・フォロワー一覧・フォロー中一覧の URL のユーザー識別子としてニックネームを使用しなければならない
- **FR-002**: システムはニックネームの解決において、一意制約と同じ正規化（小文字化・前後空白除去）で照合しなければならない（大文字小文字の違いで別ユーザー扱い・未検出にしない）
- **FR-003**: アプリ内のプロフィールへのすべての導線（マイプロフィール・タイムライン・フォロー/フォロワー一覧・バディ表示・いいね・通知・ユーザー検索結果など）はニックネーム URL を生成しなければならない
- **FR-004**: システムは ID 形式の既存 URL へのアクセスを、対応するニックネーム URL へ転送しなければならない（後方互換。フォロワー・フォロー中の下層 URL も同様）
- **FR-005**: システムは URL で表現できないニックネーム（パス区切り文字を含む等）や予約パス名と衝突するニックネームのユーザーについて、ID 形式 URL でのアクセスとアプリ内導線の ID 形式フォールバックを提供しなければならない（プロフィールに到達できないユーザーを作らない）
- **FR-006**: システムはニックネームの新規登録・変更時に、ID 形式と判別不能なパターンおよび予約パス名と同名のニックネームを拒否しなければならない（既存データは FR-005 のフォールバックで救済する）
- **FR-007**: システムはニックネーム変更時、プロフィール URL を新しいニックネームへ即時に切り替えなければならない。変更前のニックネーム URL は無効となる
- **FR-008**: システムは存在しないニックネーム・ID の URL に対して「ページが見つかりません」を表示しなければならない
- **FR-009**: プロフィールの閲覧可否・表示内容は現行と同一でなければならない（URL 形式の変更によってアクセス制御・表示範囲を変えない）

### Key Entities

- **ユーザープロフィール**: 既存機能。URL 上の識別子が ID からニックネームに変わる（データ自体の変更はなし。ニックネームの一意制約は導入済み）
- **ニックネーム**: 1〜50 文字・一意（正規化キーで比較）。設定から変更可能。本機能により URL の一部としての役割が加わる

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: プロフィール URL を見ただけで誰のページか判別できる（ニックネームが URL に含まれる）状態が、アプリ内のプロフィール導線の 100% で実現される
- **SC-002**: 機能公開前に共有された ID 形式のプロフィール URL の 100% がリンク切れにならず、正しいプロフィールへ到達できる
- **SC-003**: URL に使えない文字を含む既存ニックネームのユーザーを含め、全ユーザーのプロフィールに何らかの URL で到達できる（到達不能ユーザー 0 件）
- **SC-004**: ニックネーム変更後、5 秒以内に新しいニックネーム URL でプロフィールに到達できる

## Assumptions

- ニックネームの一意性は導入済みの一意制約（正規化キー: 小文字化 + 前後空白除去）に依拠し、本機能で新たな一意化は行わない
- **旧 URL の扱い**: ID 形式 URL は廃止せず、ニックネーム URL への転送で恒久的に維持する（通知やブックマークなど ID ベースの参照を壊さないため）
- **ニックネーム変更時**: 旧ニックネーム URL の転送・予約（取り置き）は行わない。変更後は誰でもそのニックネームを取得でき、取得者のページになる（一般的な SNS のユーザー名変更と同じ割り切り）
- **文字制約**: 既存ニックネームの文字種は変更しない（既存ユーザーへの影響を避ける）。新規登録・変更時のみ、URL 判別を壊すパターン（ID 形式・予約パス名）を拒否する。それ以外の日本語・スペース等は URL エンコードで表現する
- ユーザー検索ページなどプロフィール以外の既存 URL は変更しない
- 対象はユーザー向けアプリのみ（管理画面のユーザー詳細 URL は対象外）
