# Research: 潮回り表示（ダイビング記録・予定）

技術選定・設計判断の記録。Technical Context に NEEDS CLARIFICATION はないが、月齢の算出方法・潮名の区分方法・ロジックの配置について複数の選択肢があったため判断理由を残す。

## R1. 月齢の算出: 平均朔望月による自前の近似計算（ライブラリ・外部 API は使わない）

- **Decision**: 基準朔 `2000-01-06 18:14 UTC` からの経過日数を平均朔望月 29.530588853 日で剰余して月齢を求める純粋関数を `shared/lib/tide.ts` に自前実装する。評価時刻は対象日の JST 正午（`T03:00:00Z`）に固定する
- **Rationale**: ユーザー指定が「保存せず計算だけで実装」であり、spec FR-005 が外部サービス・外部データ非依存を要求している。月齢→5 区分の変換は ±数時間の精度で十分（区分は日単位）で、平均朔望月の近似で要件を満たす。spec の Assumptions で公式潮汐表との前後 1 日のズレを許容済み。評価時刻を JST 正午に固定するのは、日本の潮見表（JST 基準）との整合を取りつつ、`shared/lib/date.ts` と同じ文字列ベースの決定的な計算にするため
- **Alternatives considered**:
  - `astronomy-engine` / `suncalc` 等の天文ライブラリ — 真の朔望を高精度に計算できるが、日単位の 5 区分には過剰。プロジェクトは日付計算ライブラリ不採用の方針（006 R3 と同判断）で、依存追加の根拠が弱い
  - 潮汐情報 API（気象庁・海上保安庁データ等）の取得 — FR-005（外部非依存）に反する。地点選択も必要になりスコープが膨らむ
  - 真朔望の天文計算を自前実装 — 実装・検証コストが区分表示の価値に見合わない

## R2. 潮名の区分: 旧暦日相当（floor(月齢) + 1）による伝統的 5 区分表

- **Decision**: 旧暦日相当 = `floor(月齢) + 1`（1〜30）を求め、釣り暦・潮見表で一般的な対応表（[data-model.md](data-model.md) に全 30 日分を記載）で大潮・中潮・小潮・長潮・若潮に変換する
- **Rationale**: 「旧暦日 → 潮名」は日本の釣り・ダイビングで最も流通している区分方法で、ユーザーの期待（潮見表の表記）と一致しやすい。`floor` ベースのため全入力が必ず 5 区分のいずれかに落ち、境界での未分類が構造的に発生しない（spec Edge Case）。「小潮 → 長潮 → 若潮 → 中潮」の循環順序（SC-003）もこの表で保証される
- **Alternatives considered**:
  - 月齢の四捨五入で区分 — 流儀として存在するが、切り捨て + 旧暦日の方が潮見表の主流と一致する。どちらも ±1 日ズレの許容範囲内であり、より一般的な方を採用
  - 満干潮の潮位差から動的に判定 — 潮位データ（地点依存・外部データ）が必要になり FR-005 に反する

## R3. 配置: `shared/lib/tide.ts`（feature 間 import 禁止のため shared 層）

- **Decision**: 算出関数・型・ラベル定数を `service-front/src/shared/lib/tide.ts` に置く。`date.ts` / `number.ts` と同じフラットファイル + 同階層テストの慣習に従う
- **Rationale**: 利用者が `features/dives`（記録）と `features/plans`（予定）の 2 feature にまたがる。Feature-based アーキテクチャでは feature 間 import が禁止のため、共通ロジックは shared 層に置くのが唯一の正規解。`shared/lib` には既に文字列ベースの日付ユーティリティ（`date.ts`）があり、潮回りも同じ「日付文字列 → 導出値」の純粋関数として自然に並ぶ
- **Alternatives considered**:
  - `features/dives/lib/` に置いて plans から import — feature 間 import 禁止に違反
  - dives / plans それぞれに重複実装 — 旧暦日対応表の二重管理になり、区分修正時の同期漏れリスクが高い

## R4. 表示統合: 既存コンポーネントへの直接統合（新規共通コンポーネントは作らない）

- **Decision**: 新規 UI コンポーネント（TidePhaseBadge 等）は作らず、既存の DiveCard / DiveDetail / PlanList / NextPlanCardView / RecentDives / 予定詳細ページの 6 箇所それぞれに `TIDE_PHASE_LABELS[phase]` のテキストラベルを直接描画する
- **Rationale**: 表示は「区分名のテキスト（+ バッジ風の Tailwind クラス）」のみで、props も状態も持たない。コンポーネント化するとフォルダ規約（本体 + test + story + index.ts）の 4 ファイルが増える割に抽象化の利得がない（YAGNI）。各表示箇所のレイアウト（カードのメタ行・詳細の定義リスト・一覧の行）に合わせた微調整は統合先でやるほうが自然
- **Alternatives considered**:
  - `shared/components` に TidePhaseBadge を新設 — 表示スタイルを 5 箇所で完全統一したくなった時点で抽出する。現段階では過剰
  - 一覧クエリ側で潮回りを付与して返す — 表示専用の導出値をデータ取得層に混ぜると関心が分離できない。表示時に呼ぶ方が「保存しない導出値」の意図に合う
